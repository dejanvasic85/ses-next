## Diagnosis log - the August click collapse

Work done 2026-09-10 and 2026-09-11 against issue #695. This section is the record of the month's
SEO work for invoicing, because the diagnosis ran through Search Console and curl
and left no commit trail of its own.

### What we set out to test

August's scorecard found clicks and phone leads falling while rankings held or
improved. The leading hypothesis was the design-system and nav rebuild (PR #648/#650,
30 July) and the services hub redesign (PR #671/#672, 8 August), both of which shipped
inside the measurement window. Issue #695 set two checks before any new content work:
are Google's snippets stale, and does the click-to-call event still fire.

### Check 1 - stale SERP snippets: ruled out

URL Inspection on `/locations/electrician-seddon` came back healthy. Last crawl
3 September, well after both rebuilds. Page fetch successful, page indexed, canonical
correct. A `site:sesmelbourne.com.au` search showed current, well-formed snippets
across the home, services, blog, FAQ and terms pages. Snippets are not the problem.

### Check 2 - the unstyled screenshot: a red herring, but it surfaced a real bug

The Inspection Tool's rendered screenshot showed the page completely unstyled: nav as
a bullet list, blue underlined link text, an unsized phone icon filling the viewport.

We first traced this to `robots.txt`, which carried `Disallow: /_next/` and so blocked
every stylesheet and script the site serves. That is a genuine problem and we fixed it
(PR #725), because Google cannot assess layout or mobile-friendliness on a page whose
CSS it is not allowed to fetch.

But it was not the cause of the unstyled screenshot. After the fix deployed, a fresh
Live Test rendered exactly the same way. Digging into the served CSS explains why:
the site is on Tailwind v4, and 95.7% of the stylesheet sits inside `@layer` blocks.
The Inspection Tool renders with an older Chromium than live Googlebot, and a renderer
without CSS cascade-layer support drops every layered rule, keeping only the 4.3%
remainder. That is precisely the page in the screenshot.

So the screenshot could not have looked any different, before or after the fix. It is a
limitation of the inspection renderer, not evidence about what live Googlebot sees.
Live Googlebot runs an evergreen Chromium that has supported cascade layers since
Chrome 99.

**Correction to our own reasoning:** we initially read the unstyled screenshot as proof
of a rendering failure and named the robots block as the leading cause of the August
collapse. That was overstated. The robots fix was still worth shipping on its own
merits, but it should not be treated as the explanation for the click drop, and the
August collapse remains unexplained.

Practical consequence: URL Inspection cannot verify rendering on this site. Use Search
Console's Core Web Vitals and Page Experience reports, which reflect real Chrome users,
or judge from impressions and positions directly.

### Check 3 - click-to-call: two separate problems, and the lead drop is explained

**The markup was broken.** The phone link rendered as `href="tel:0415 338 040"` with raw
spaces, which is invalid in a `tel:` URI and breaks click-to-call on mobile. Fixed in
PR #725.

**But that was not what made the lead numbers fall.** Testing the live site in GTM
Preview showed the tags fire correctly, and the event they send is `link_click`, not
`first_time_phone_call`. Searching the codebase and the full git history turns up no
`first_time_phone_call` anywhere in application code. It is defined in GA4 or GTM, not
in the repo, and it matches on the phone number.

GA4's own chart dates the break precisely. `first_time_phone_call` ran at 1 to 3 per day
through June and July, then **flatlines to zero on 30 July and never recovers**, right
through September. That is not a decline in demand, it is a counter being switched off.

30 July is the design-system and nav rebuild (PR #648/#650). Karl's Sanity phone-number
change followed on 3 August at 09:47 UTC (confirmed from the live `siteSettings`
document), from (03) 4050 7937 to 0415 338 040. Either would break a number-matching
rule, but the chart points at the nav rebuild, and the Sanity change would have kept it
broken regardless.

August's window ran 27 July to 23 August, so the counter was alive for about the first
three days of it. `first_time_phone_call` read 23 down to 2, which is the shape you would
expect.

We could not find where the event was ever defined. It is not in the codebase, not in
GA4's created events, and no current GTM tag sends it. Most likely a GTM tag that the
nav-rebuild work changed or removed.

**So August's "lead collapse" was a measurement break, not a business one.** Real calls
most likely held. PR #661 on the same day fixed the visible half of this, the stale
number in page metadata; the tracking half went unnoticed.

The August scorecard's lead figures should be read with this in mind. Its click findings
are unaffected and still unexplained.

### The fix: a custom event that cannot break this way

Any GTM trigger keyed on the phone number breaks the next time Karl changes it, and our
own E.164 fix in PR #725 would have broken it again. So the site now pushes a custom
`phone_call_click` dataLayer event on every call tap, through a shared `CallLink`
component used at all six call sites. The event carries no phone number, so it keeps
matching regardless of what the number is.

**Done in GTM on 13 September.** A `Click - Phone call` custom event trigger and a
matching GA4 event tag now send `phone_call_click` to `G-TSF7M92YC1`. Verified in GTM
Preview and the container is published. The `Click - Telephone links` trigger, which
feeds the Google Ads phone conversion, still matches `tel:04` and should be loosened to
`tel:` so it survives the next number change.

The property has no key events configured beyond GA4's unused `purchase` default, so
`first_time_phone_call` was never a key event and retiring it needs no action. From this
scorecard onward the phone metric is `phone_call_click`.

**Trend-line note for future scorecards:** `phone_call_click` starts from zero on
13 September. June through September phone figures are not comparable with October
onward. October is the first clean month.

### Also found

- The phone number in the Seddon page's meta description, (03) 4050 7937, did not match
  the 0415 338 040 in the page body. Same root cause as the tracking break above: the
  number changed in Sanity and some copy still referenced the old one.
- The FAQ page's meta description double-escapes an ampersand. It reaches the live SERP
  as `solar &amp; more`.
